# 登记交换服务
运行 python3 -m lab.provider --port 8765。GET /view 返回冻结 epoch、revision、ceiling；GET /summary 与 /bundle 均要求 epoch、revision、lower、upper 查询参数，范围闭区间。摘要是现有 feeds.bundle.segments 的 canonical 二元组摘要，事件包使用原生 bundle 格式。POST /control 接收 {"expire":true}，使旧 revision 返回 410。数据为 32 条独立资产登记，序号与摘要可直接复核。服务仅模拟只读远端，不操作本地台账。

## 区间补采（backfill）
Registry Bridge 通过 registry_bridge.reconcile.exchange.ExchangeClient 访问上述只读接口，并由 registry_bridge.reconcile.backfill.BackfillManager 把区间摘要与事件包导入连成一次有证据的补采。流程与命令入口（均走现有 call 操作或 `backfill` 子命令）：

1. `backfill.plan`：先请求一次 /view，冻结本轮 epoch、revision、ceiling 并写入 backfill_runs，按 segment_width 切出初始工作区间。之后所有 /summary、/bundle 请求都携带该冻结视图，整轮结论不拼接两个视图。
2. `backfill.execute`：对每个区间请求 /summary，与本地同序号 fingerprint 序列的 canonical 摘要比对。摘要相同的区间标记 matched 且绝不下载事件包；摘要不同的非叶子区间二分收窄（本地完全为空的稀疏区间直接整段 /bundle 补回，避免逐序号请求）；叶子区间才下载 /bundle。
3. 不可变冲突：本地同序号已存在另一份事件（同 event_id 不同内容或同序号不同事件）时，receive 保留本地事件并在 conflicts 表登记双方证据，区间标记 conflicted 并停止该区间的自动处理；其他区间继续。冲突区间不会被写成 matched/backfilled。补齐的前序事件仍由现有连续序列投影（drain_stream）决定是否生效。
4. 视图过期：冻结 revision 收到 410 时，运行标记 expired、保留未完成工作清单；execute 不会改用新 revision，需重新 plan 生成新 run。网络或协议故障标记 paused，工作清单持久化。
5. 请求预算：每个 HTTP 请求都计数并持久化（requests_used/request_budget）。预算耗尽时 paused 退出；`backfill.extend_budget` 提高预算后再次 execute 即从持久化工作清单继续。已导入的事件包记录在 backfill_bundles，重启后不重复生效。
6. `backfill.status` / `backfill.list` 查询运行记录：state、pause_reason、实际请求数、各类范围计数（matched/backfilled/conflicted/未完成）、对应序号数量，以及台账游标、阻塞原因和缺口。

演示运行 `python3 -m lab.backfill_demo`，覆盖稀疏缺口、不可变冲突、视图过期、预算耗尽后重启续跑，并在末尾核对业务台账与区间对账结论。
